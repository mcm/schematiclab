# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Schematiclab is a Next.js 16 / React 19 app (pnpm) that converts Minecraft schematics between formats and Minecraft versions, entirely client-side. It has two modes: Simple Mode (`src/app/page.tsx`: drop a file, pick an output format and version, download) and the Advanced Editor (`src/app/advanced/page.tsx`: 3D preview, material list, block swaps, version-mapping preview, and CurseForge mod loading so modded blocks render).

## Commands

```bash
pnpm dev                 # next dev
pnpm build               # production build (output: "standalone")
pnpm test                # vitest run (all tests)
pnpm exec vitest run src/lib/__tests__/convert.test.ts   # single file
pnpm exec vitest run -t "name of test"                   # by test name
pnpm lint                # eslint
pnpm typecheck           # tsc --noEmit
pnpm format              # prettier --write . (CI runs prettier --check)
```

CI (`.github/workflows/ci.yml`) requires lint, the prettier check, typecheck, `vitest run --coverage`, build, Semgrep (`--config auto` + `p/trailofbits`, errors fail the build) and TruffleHog. Run lint, format and typecheck before calling work done.

Tests run in the `node` environment (`vitest.config.ts`) and include only `src/**/*.test.ts`. IndexedDB code is tested with `fake-indexeddb`. Binary schematic fixtures live in `src/lib/__tests__/fixtures/`.

### Codegen (rarely needed)

These scripts use `node --experimental-strip-types` and expect sibling checkouts of external data repos (`~/projects/minecraft-data` / `../minecraft-data`, plus `misode/mcmeta`; you can point at other locations with `MINECRAFT_DATA_PATH` and `MCMETA_PATH`):

- `pnpm gen:translations` regenerates `src/lib/schemlib/data/block-translations.generated.ts`, `vanilla-property-domains.generated.ts` and `forge-1.12-flatten.generated.ts`. Don't hand-edit `*.generated.ts`. Change `manual-overrides.ts` or `forge-1.12-specs.ts` and regenerate.
- `pnpm gen:mc-assets` rebuilds the vanilla 3D-preview bundle in `public/minecraft-assets/` (texture atlas, UVs, blockstates, models, opaque-block list).
- `scripts/regenerate-known-versions.mts` regenerates `schematic-formats/known-versions.ts`.
- `pnpm gen:camo-shapes` regenerates the camo shape packs in `public/camo-shapes/` (schema: `src/lib/render/camo/shape-pack.ts`). It needs a FramedBlocks checkout (`~/projects/FramedBlocks` or `../FramedBlocks`, override with `FRAMEDBLOCKS_PATH`). It reads the checkout's `framed_templates/*.json` and `BlockType.java`, plus the hand port of `TemplateSpecs.java` and the double blocks' `calculateParts()` in `scripts/camo-shapes/framedblocks/template-specs.ts`, and hand ports of the bespoke `*Geometry.java` classes (walls, panes, torches, signs…) in `scripts/camo-shapes/framedblocks/geometry-specs.ts`, with one file per sloped package next to it (`slope.ts`, `slope-edge.ts`, `prism.ts`, `pyramid.ts`, `slope-slab.ts`, `slope-panel.ts`, `slope-panel-corner.ts`, `stairs.ts`, `rail-slope.ts`), each holding its geometries and its double blocks' `calculateParts()`. It also uses vanilla models from `public/minecraft-assets/models.json`. The pack records the FramedBlocks commit, `mod_version` and license. The script prints every `BlockType` id that has no shape entry. Re-run it for each FramedBlocks release. When a release changes `TemplateSpecs`, a `calculateParts()` or a ported `*Geometry.java`, update the port first. It also writes `copycats.json` and `create.json` from Copycats+ and Create checkouts (`~/projects/copycats` / `../copycats`, override with `COPYCATS_PATH`; `~/projects/Create` / `../Create`, override with `CREATE_PATH`). Those run hand ports of the Copycats+ `*ModelCore.java` classes in `scripts/camo-shapes/copycats/` (one file per Java package, on a port of the Copycats+ assembly API in `assembly.ts`) and of Create's copycat models in `scripts/camo-shapes/create/`, and print the block ids without a shape entry. Re-run and re-port the same way for each release of either mod.
- `pnpm gen:camo-fixture-datapacks` writes two datapacks to `build/camo-fixture-datapacks/` (FramedBlocks on 26.1.2; Copycats+ and Create on 1.21.1). They place every camo block in-game so the mods save the camo fixtures themselves; each pack's README has the steps. FramedBlocks states come from the checkout's Java and the shape pack's rules. Copycats states are hand-written in `scripts/camo-fixtures/copycats-specs.ts`. The script also needs the `copycats` and `Create` checkouts (`COPYCATS_PATH`, `CREATE_PATH`).
- `pnpm gen:camo-block-states` reads the camo fixtures in `src/lib/__tests__/fixtures/` and writes `src/lib/camo/camo-blocks.generated.ts` (the blocks that save camo, and the FramedBlocks double blocks with a `camo_two` slot) and `src/lib/camo/block-properties.generated.ts` (each camo block's state properties, values as sampled in the fixtures). Re-run it after re-saving the fixtures.
- `pnpm gen:everycomp` regenerates the Every Compat, Stone Zone and Gems Realm module tables in `src/lib/mods/generated/everycomp/tables/` from checkouts of those mods and Moonlight (see "Every Compat, Stone Zone and Gems Realm" below).
- `pnpm gen:ucw-fixture-functions` writes a Minecraft 1.12.2 world function to `build/ucw-fixture-functions/` (`data/functions/schematiclab/ucw_fixture.mcfunction`, run as `/function schematiclab:ucw_fixture`, plus a README with the in-game steps). It places every block of the rules in Unlimited Chisel Works' bundled `ucwdefs/chisel/natura.json` and `environmentalmaterials.json` (one rule per layer, one row per `from` meta, the `from` block beside 16 variations) and a structure block preset to save the area as `ucw_1_12_2.nbt`. It needs a UCW checkout (`~/projects/UnlimitedChiselWorks` / `../UnlimitedChiselWorks`, override with `UCW_PATH`). Rules are parsed and named with the app's own `src/lib/mods/generated/ucw/rules.ts` (keep it import-free so node can load it); layout and commands are in `scripts/ucw-fixtures/layout.ts`.

## Architecture

### schemlib (`src/lib/schemlib/`)

This is a TypeScript port of a Python library, and file headers name the Python original. Every format extends `AbstractSchematic`/`AbstractRegion` (`schematic-formats/abstract.ts`), which provide static `schematicLoad`, `fromSchematic(other, targetVersion)` and `getDefaultExtension`, plus instance `schematicDump`. Conversion always goes through `IntermediateSchematic` (`intermediate.ts`), so a new format only needs to convert to and from the intermediate form. `detect.ts` (`detectSchematicType`) sniffs bytes as JSON, then NBT, then SNBT. The ids it returns (`"Sponge[v2]"`, `"BuildingGadgets2[1.20+]"`, and so on) are stable identifiers used across the whole app. NBT and SNBT codecs are hand-written (`nbt.ts`, `snbt.ts`).

**`FORMATS.md` is the source of truth** for format ids, canonical extensions (one per format family) and output rules. The `JSON` intermediate format is dev-only and must never appear as an output choice in production UI.

Version translation lives in `schematic-formats/version-mapping.ts` and `data/translate.ts`. It walks a codegen'd chain of per-anchor-version block-state diffs (one anchor per major.minor up to 1.20.1, then one per release that changed blocks, since Mojang now ships block changes in patch "drops"; add new ones to `ANCHOR_VERSIONS` in `data/types.ts` and regenerate), uses a flatten table for 1.12 ↔ 1.13, and chains Forge 1.12 `name[variant=...]` states through `id:meta`. Lossy translations report through `onWarning`. Doors get a cross-block fixup (`fixupDoors`) after per-block mapping.

The Advanced Editor's Version Mapping tab layers modded mapping on top (`src/lib/advanced/`). `mod-namespace-status.ts` turns namespace mappings, loaded files, `resolveModFileForVersion` results (`curseforge/resolve-file.ts`, which prefers the source file's loader and reports a loader fallback) and the user's per-(target version, namespace) replace/keep choices into a plain-data `ModMappingContext`: per namespace `unmapped`, `target` (blocks of the mod's target-version file), `replace` (`oldns:path` → `newns:path`), `keep` or `pending`. `previewVersionMapping` and `applyVersionMapping` both go through `resolveModdedState` (`mod-mapping.ts`), so preview and apply agree: missing blocks, declined or unmapped mods become problematic rows with a `reason`, blockstates are corrected best-effort (`invalid-state`), and pending files block Apply (`applyReadiness`). A mod block's `properties` come from its blockstate JSON, which only lists the values that pick a model (a multipart fence never mentions `north=false` or `waterlogged`). So `fitProperties` treats them as partial evidence: `mods/property-domains.ts` completes them at read time (booleans, then the smallest vanilla value set from `vanilla-property-domains.generated.ts`), and a property or value is dropped or replaced only if the mod's file for the schematic's version (`sourceBlocks` in the context) shows it mattered. Without that file, unknown property names that vanilla also uses are kept. Stored `properties` stay as observed. Namespaces absent from the context take the vanilla translator path. The target version may be null, in which case only mod rewrites run and `minecraftVersion` is kept. Vanilla translation, mod rewrites and overrides apply as one step with one undo snapshot. "Suggest a block" (`suggest-blocks.ts`) ranks candidates that exist in the target version (`vanillaBlocksForVersion` from the codegen'd data plus mapped/replacement mod files) by OKLab distance within the same full-cube class, falling back to name similarity. The replacement picker's autocomplete is scoped the same way: `searchBlockCatalog`/`isCatalogedBlockId` take a `CatalogScope` (vanilla blocks of that version, and mod files loaded for exactly that version; a mod with no file for it offers no blocks). Vanilla colours come from `public/minecraft-assets/block-colors.json` (written by `pnpm gen:mc-assets`, maths in `render/block-appearance.ts`), and mod colours are computed at jar load into `ModBlock.appearance` (`ensureModAppearances` backfills older files).

### Worker boundary

`src/lib/convert.ts` is the only orchestration API the UI uses. It must stay worker-safe (no DOM). In production it runs inside `convert.worker.ts`, and the main thread calls it through `convert-client.ts` (`detectInWorker`, `convertInWorker`, `parseInWorker`, `cancel`). Schematic class instances can't be structured-cloned, so the worker returns a plain `ParsedSchematicProjection`: palette with counts, plus per-region placements that index into the palette, with air excluded. Editor edits such as block swaps (`swap-projection.ts`) operate on that projection, and export re-serializes it via `serializeSchematic`. Mod jars use the same pattern with `mods/mod-jar.worker.ts` and `mod-jar-client.ts`.

### Client state

State lives in module-level stores that components subscribe to with `useSyncExternalStore`, not in React context. `editor-state.ts` holds the staged file and parse status. It survives client-side navigation between `/` and `/advanced` but resets on reload. Heavy edit and undo operations live in `editor-state-edits.ts` (swap and translation snapshots are tracked separately) so they stay out of the `/` bundle. Keep bundle splits in mind: code imported by Simple Mode shouldn't pull in deepslate or the advanced editor. That's why `invisible-blocks.ts` is its own module.

### Mods and CurseForge

- Server routes (`src/app/api/curseforge/**`) proxy CurseForge. Shared validation, upstream fetch and payload trimming live in `lib/curseforge/server.ts`. The download route streams jars up to `CURSEFORGE_MAX_JAR_BYTES`. `lib/curseforge/client.ts` is the browser side and handles retries of transient failures, including `Retry-After`.
- `mods/load-mod.ts` runs the load pipeline: pick a file, download, parse in the worker, then register and persist. `parse-mod-jar.ts` only inflates `assets/*/{blockstates,models,textures,lang/en_us.json}` and `assets/framedblocks/framed_templates/*.json` behind zip-bomb size limits. It never loads class files. It keeps only models and textures a blockstate can reach, read both the 1.13+ way and the 1.12 way (`legacyBlockstateRefs`: model names gain `block/`, Forge `forge_marker` variants set `textures` themselves). A pre-1.13 file stored before that has no models or textures, so it gets a "reload" warning at hydration (`legacyAssetsRead`, `withLegacyAssetsWarning`). A loaded jar's FramedBlocks templates replace the shape pack's pieces of the same template (`render/camo/template-overrides.ts`), using the `template` tags `gen:camo-shapes` puts on template-derived pieces.
- `mods/registry.ts` is the reactive set of loaded mod files. It hydrates from IndexedDB (`mods/store.ts`) and falls back to in-memory storage when IndexedDB is unavailable. It holds one file per (CurseForge mod, Minecraft version), keyed `loadedModKey` = `${modId}:${gameVersion}`, so a mod's source and target files coexist; in-flight loads in `load-mod.ts` use the same key (`modLoadKey`). Look up files with `getLoadedModFile`, `getModBlocksForVersion` and `getPreviewModFiles` (one file per mod, for the 3D preview). The store keeps textures, models and blockstates content-addressed (SHA-256) in a shared `blobs` object store, and per-file asset records hold hashes. Removing or replacing a file garbage-collects blobs nothing else references. IndexedDB upgrades can't await `crypto.subtle`, so the v2 → v3 migration parks old assets and converts them after `openDB` resolves.
- `mods/mappings.ts` is the reactive namespace → CurseForge project mapping store (`useNamespaceMappings`), persisted in the same DB (`namespaceMappings`) with an in-memory fallback. A namespace maps to one project, and a project can own several namespaces. A successful load auto-maps the file's unmapped namespaces (`autoMapNamespaces`) without overwriting existing mappings. Keep its interface narrow (SCHEM-54 may change the backing). The advanced page owns the one shared `ModProjectPicker` (`components/mod-project-picker.tsx`, map or replace mode, preselects only an exact slug match), and panels ask for it through `onMapNamespace` / `onRequestProjectPicker`.
- Simple Mode must not import any of this (mappings, the picker, suggestions, modded mapping). `src/lib/__tests__/simple-mode-imports.test.ts` walks `src/app/page.tsx`'s import graph and guards it.

### 3D preview (`src/lib/render/`)

The preview uses deepslate. `minecraft-resources.ts` fetches the vanilla bundle from `public/minecraft-assets/` and rebuilds a combined texture atlas and model set whenever the set of preview files changes. It uses exactly one file per mod (`getPreviewModFiles`): the file for the schematic's current version when loaded, else the most recently loaded one. Layout (`atlas-layout.ts`, capped at a power-of-two size, downscales textures when they don't fit) and resource assembly (`block-resources.ts`) are pure and unit-tested. Only pixel drawing touches the DOM. Modded blocks that can't be rendered fall back to a magenta/black "missing" cube instead of disappearing; in a `variants` blockstate only the unrenderable variants do. 1.12 mod blockstates (Forge `forge_marker`, unprefixed model names) are rewritten for deepslate by `modernizeLegacyModAssets` (`mods/generated/legacy-blockstate.ts`, one synthesized model per Forge variant), which block appearances also use, and 1.12 vanilla texture names (`minecraft:blocks/planks_oak`) map to the bundle's 1.13+ names through the hand-written rename table in `mods/generated/legacy-textures.ts`.

The preview card's "Static Renders" tab (`components/static-renders.tsx`) draws a contact sheet on a 2D canvas, with a PNG download. It doesn't use deepslate. It shows four isometric views, front/side/top elevations, two plan slices and a cutaway. Blocks are flat-coloured cubes. Colours come from `block-colors.json` and `ModBlock.appearance` (camo blocks use their camo's colour, `static-render-colors.ts`), and blocks with no colour data get a stable colour hashed from their id. The geometry (`static-views.ts`) and the layout (`contact-sheet.ts`) are pure and unit-tested.

### Camo blocks

FramedBlocks (26.1.2) and Create/Copycats+ copycats (1.21.1) take their look from a camo block stored in their block entity.

- **Block entities in the projection:** each `ParsedSchematicRegion` carries `blockEntities` (`pos` plus chunk-format `nbt` without `x`/`y`/`z`). `src/lib/camo/` is worker-safe and must not import from `src/lib/render/`. `extract.ts` reads each mod's NBT into one ordered slot list, `materials.ts` fills the palette's `camoMaterials` for the material list, `swap.ts` does camo swaps and `write.ts` is the only place that writes camo NBT (swaps and the version translation in `version-mapping.ts` both go through it). `block-entity-type.ts` decides whether a parent-row swap keeps the block entity.
- **Editing camo:** the material list shows each camo block's materials, plus one "empty" material for its empty slots. A camo block without a block entity (just swapped in from another block) counts every slot as empty (`placedCamoSlots`, slots from `camo-blocks.generated.ts`). Swapping the empty material fills the slots, creating the block entity (`newCamoBlockEntity`) when needed, and a null target removes a camo. Both share "Undo last swap". When the swap picker's target is a camo block, it keeps the source's properties that the target also has (`carryCamoBlockProperties`, from `block-properties.generated.ts`). Typed `[name=value]` properties override them. The picker resolves one target per source state (`BlockStatePickerChoice.targets`): a Version Mapping group's states, or every state of the block when "Replace all N states" is ticked in the material list (`swapBlockStates`, one undo step). With `allowCamo`, a camo block target also gets camo inputs per slot (`CamoChoice`); swaps and version-mapping overrides (`VersionMappingOverride.camo`) write it with `writeCamoChoice`. A version-mapping override to a camo block never applies to camo states.
- **`__camo` injection:** deepslate's `ChunkBuilder` only passes id and properties to `getMesh`, never NBT. So the preview adds a synthetic `__camo` property to each camo-capable block. Its value indexes a `CamoTable` (`render/camo/camo-table.ts`) of unique block state + camo slot combinations, and `CamoBlockDefinition` (`camo-definition.ts`) looks the camo up there. It meshes the camo as a full cube and cuts the block's shape out of it with `mesh-crop.ts` (slopes run `quad-ops.ts`). Deepslate itself is unchanged. The "Show camo" toggle (`show-camo-state.ts`) swaps in a frames-only table.
- **Shape packs:** `public/camo-shapes/<namespace>.json` (schema and `validateShapePack` in `shape-pack.ts`, bump `formatVersion` on incompatible changes) hold per-block, per-state rules of pieces. `pack-loader.ts` fetches a pack lazily, only once its mod's namespace is loaded, and at most once per session. Packs are generated, never hand-edited, and each records its source repository, commit, mod version and license. Keep `public/camo-shapes/NOTICE.md` in step with them.
- **Fallbacks:** no pack, an invalid pack or no rule for the state renders a full cube of the frame texture. An empty slot renders the shape in the frame texture (`framed_block`, `framed_block_alt` for the second slot, `create:block/copycat_base`). An unknown camo block renders the shape in the missing texture.
- **Fixture-coverage test:** `render/camo/__tests__/fixture-coverage.test.ts` parses every camo fixture in `src/lib/__tests__/fixtures/` (listed in `CAMO_FIXTURES.md`) and fails when a camo-capable placement has no matching rule. The fixtures were saved in-game by the mods themselves. A new fixture must be added to its `FIXTURES` list.
- **Per-release regeneration:** update the mod's checkout (`FRAMEDBLOCKS_PATH`, `COPYCATS_PATH`, `CREATE_PATH`) and update the hand ports if the release changed the Java they port. Then run `pnpm gen:camo-shapes` and check the ids it prints without a shape entry, run `pnpm gen:camo-fixture-datapacks`, re-save the fixtures in-game with the datapacks (see each pack's README and `CAMO_FIXTURES.md`), copy them into `src/lib/__tests__/fixtures/`, run `pnpm gen:camo-block-states`, and run `pnpm test`.

### Generated blocks

Some mods register blocks at runtime instead of shipping them in their jar, so the jar has no blockstates, models or textures for them. Each such mod needs a hand-ported **generated-block provider**. There are two kinds so far: Unlimited Chisel Works (UCW, 1.12.2 Forge, LGPL-3.0), and the Every Compat family (Every Compat "Wood Good", Stone Zone, Gems Realm; 1.21/1.21.1; Supplementaries Team License). Each provider decides its own supported Minecraft versions.

- **Framework (`src/lib/mods/generated/`):** worker-safe, no DOM (from `src/lib/render/` only the pure `block-appearance.ts` helpers; `__tests__/registry.test.ts` checks this). `types.ts` defines `GeneratedBlockProvider`, keyed by namespace. Given the `GeneratedBlockFiles` of one Minecraft version (loaded files, their blocks, assets, `providerData`, vanilla assets), a provider `enumerate`s the blocks it can produce, `resolve`s an id and properties to `resolved` (a synthesized `ModBlock`, blockstate, models and `GeneratedTextureRecipe`s, plus `approximate`), `needs-mods` (namespaces and source blocks to load, optional `fallbackModels`) or `unrecognised`, and runs a recipe on decoded source images (`generateTexture`). Register a provider in `BUILTIN_PROVIDERS` (`registry.ts`). Preview, catalog, material list and mapping code only use `registry.ts`, so a new provider touches none of them. Resolution is sync and only sees assets already in memory: call `await loadGeneratedBlockFiles(version)` first and re-render on `subscribeGeneratedBlockFiles`.
- **Rule data in jars:** a provider that ships data in a jar adds a `ProviderJarReader` to `PROVIDER_JAR_READERS` (`jar-data.ts`). `parse-mod-jar.ts` inflates its entries under the same zip-bomb limits and stores the result in `providerData[<namespace>]`, persisted inline by `mods/store.ts`. UCW reads `assets/unlimitedchiselworks/ucwdefs/**/*.json` (`ucw/rules.ts`, a port of UCW's rule parsing; keep it import-free, since `gen:ucw-fixture-functions` loads it). The UCW jar has no blocks of its own, so a jar whose rules generate blocks is accepted anyway. A UCW file stored before rules were read gets a "reload" warning at hydration.
- **UCW resolution (`ucw/resolve.ts`):** ids are `unlimitedchiselworks:<through>_<from>_<from meta>` (`ucwBlockId`, port of `UCWBlockRule`), and a UCW block's states are its `through` block's states. A rule applies only when every mod in its file's `modid` list is loaded. The `from` meta is known only to the `from` mod's Java, so `ucwMetaStates` takes, in order: `ucw/meta-overrides.ts` (hand-written block id → ordered states, exact), the Forge 1.12 flatten table for `minecraft:` blocks (exact), Chisel's blocks (`ucw/chisel.ts`, exact), then the order the block's blockstate JSON lists its variant values, which is flagged `approximate`. `iterate` lists use that order and explicit `state` lists their listed order. When a saved fixture shows a different `from` state for a meta, add an override entry. Chisel's `variation=N` → blockstate variant order only exists in Chisel's Java, so it is hand-ported in `ucw/chisel.ts`. 1.12 vanilla and Forge `forge_marker` blockstates are read by `legacy-blockstate.ts`.
- **UCW models and textures:** `ucw/model.ts` synthesizes, per `through` state, a model parenting the `through` model with every texture remapped to a generated one (`UCWProxyClient`, `UCWVanillaModelRemapper`). `ucw/source-texture.ts` ports `UCWMagic.getLocation`, and `ucw/recolour.ts` and `ucw/colorspace.ts` port `UCWMagic.transform` and `UCWColorspaceUtils` bit-for-bit (float32 via `Math.fround`; check changes against the real Java with `javac`/`java`). UCW's "LAB" has no sRGB gamma step, so don't use the OKLab helpers.
- **Integration:** the 3D preview calls `setMinecraftResourcesBlocks` with the palette, and `render.ts` (`loadGeneratedBlockRender`) adds the generated blockstates, models and textures to `assembleResources` and the atlas. Textures are cached by `generatedTextureCacheKey`, so atlas rebuilds don't redo the recolouring. Static Renders, the material list and "Suggest a block" read appearances from `block-store.ts` or `loadGeneratedBlockSetsWithAppearances`. `block-catalog.ts` adds a version's enumerated blocks to scoped search. The material list labels rows with `labels.ts` (`generatedBlockLabel`: display name, provider name, the `APPROXIMATE_GENERATED_BLOCK_HINT` badge, and the needs-mods message). Version Mapping precomputes provider results on the main thread (`advanced/generated-mapping.ts`), because `ModMappingContext` crosses into the worker. `resolveModdedState` checks them before `missing-block`: resolved blocks are fitted like file blocks, and unresolvable ones get `generated-sources-missing` with the needs-mods message. Namespaces still loading are `pending`.
- **Fallbacks:** a recognised block whose source mods are missing renders its `through` block un-recoloured when that block is loaded (`fallbackModels`), else the missing cube. An id no provider recognises stays an ordinary missing mod block (`missing-block` in Version Mapping). Not supported: user `config/ucwdefs` rules, CTM, `has_color` tinting and `custom_*_class` behaviour.
- **Fixture-coverage test:** `mods/generated/__tests__/ucw-fixture-coverage.test.ts` parses `ucw_1_12_2.nbt` (documented in `GENERATED_FIXTURES.md`; there is no Litematica save) with hand-written rules and a synthetic loaded-file set, and checks every UCW placement resolves to the `from` state saved at x=0 of its row. A mismatch gets a `meta-overrides.ts` entry naming the fixture.
- **Per-release steps (UCW):** update the UCW checkout (`UCW_PATH`). If `UCWMagic`, `UCWColorspaceUtils`, `UCWBlockRule`, `UCWProxyClient` or the rule parsing changed, update the ports (`recolour.ts`, `colorspace.ts`, `source-texture.ts`, `rules.ts`, `model.ts`) and their goldens, and update `ucw/chisel.ts` if Chisel's `Features.java` changed. Then run `pnpm gen:ucw-fixture-functions`, re-save the fixtures in-game with the function (see its README), copy them into `src/lib/__tests__/fixtures/`, add override entries for any meta mismatch, and run `pnpm test`.

#### Every Compat, Stone Zone and Gems Realm (`src/lib/mods/generated/everycomp/`)

These addons cross a supported mod's blocks (furniture, Chipped, Rechiseled, Macaw's…) with every block type the loaded mods add: Every Compat with wood and leaves types, Stone Zone with stone and mud types, Gems Realm with gem, metal, crystal and dust types. Block ids are `<addon>:<shortId>/<type namespace>/<entry name>`, e.g. `everycomp:af/biomesoplenty/fir_chair`. One shared engine runs three providers (`EVERYCOMP_PROVIDER`, `STONEZONE_PROVIDER`, `GEMSREALM_PROVIDER` in `provider.ts`). They only apply to `EC_GAME_VERSIONS`, and only when the addon's own jar is loaded: its masks and hand-made textures live there, its loader picks the fabric or neoforge modules, and its `block_type.*` lang names the blocks. The license allows copying parts of the code into a non-competing project with credit, so every ported file credits the authors. Never commit the mods' textures.

- **Module tables (`tables/*.generated.ts`, `pnpm gen:everycomp`):** the mods keep their block definitions in Java builder chains (`SimpleEntrySet.builder(...).addTexture(...)...`), one module per supported mod. `scripts/generate-everycomp.mts` reads the module registrations, the chains (base type, name/prefix, `TextureInfo`s with masks, overlays and palette strategies, merged palettes, conditions, model transforms), the hardcoded sprites (`CompatSpritesHelper`, `SpriteExtra`) and Stone Zone's hardcoded models. It needs checkouts of `MehVahdJukaar/WoodGood` (`EVERYCOMP_PATH`, else `~/projects/everycomp` or `../everycomp`), `MehVahdJukaar/StoneZone` (`STONEZONE_PATH`), `Xelbayria/GemsRealm` (`GEMSREALM_PATH`) and `MehVahdJukaar/Moonlight` (`MOONLIGHT_PATH`). `addModelTransform` and `addCondition` lambdas are parsed (`scripts/everycomp/java.ts`) and translated to TypeScript with a whitelist of calls (`emit.ts`). They run against `runtime.ts` (`J` for Java `String` semantics, `EcResTransformer`, the `EcTypeView`/`EcContext` the lambdas see). Registration guards (`if (isModLoaded…)`) must be known to `readGuard` (`modules.ts`); an unknown one fails the script. Anything it can't translate is printed and recorded as `unsupported` on the entry set. Don't hand-edit the tables.
- **Block types (`block-types/`):** a port of Moonlight's wood and leaves detection (`WoodTypeRegistry`, `LeavesTypeRegistry`, `HardcodedBlockTypes`) and of Stone Zone's and Gems Realm's registries, including finders and blacklists. It works from a `BlockTypeWorld` (`world.ts`): vanilla blocks, then the loaded files' blocks, item ids (`LoadedModAssets.items`, read from item models), loaded namespaces as "mod loaded", and blockstates and models. The runtime-only checks (block classes, property counts, axe stripping, note-block instruments) are approximated in `approximations.ts`. The main child of every stone, mud and Gems Realm type is `block`.
- **Resolution (`state.ts`):** an `EcAddonState` per addon and files view holds the active registrations, the type views and the "does this entry set generate this block" check (`generatedBlock`: the entry set's condition plus `isEntryAlreadyRegistered`, without the per-mod hardcoded tables). Ids are parsed back with the entry set's name scheme. An id whose addon, supported mod or type mod isn't loaded is `needs-mods`, with the template block as the fallback when it is loaded.
- **Assets (`assets.ts`):** the template block's blockstate and the non-vanilla models it names are re-serialized and rewritten as text by the addon's transformers (EC `makeModelTransformer`/`makeBlockStateTransformer`, Stone Zone's and Gems Realm's own), including `replaceWithTextureFromChild`, which swaps in a child's texture (`findFirstBlockTexture`: Moonlight's `TextureCache` with Java `HashSet` order, special textures first, then guesses). Each `TextureInfo` becomes a recipe named the way `TextureGenHelper` names it. Textures a loaded jar already ships at that id are skipped ("add if not present").
- **Textures (`texture/`):** a port of Moonlight's `Palette`, `Respriter`, colour spaces, `Mth` and `SpriteUtils`, and of every palette strategy the three mods use (`strategies.ts`, keyed `<repo>:<Class>.<FIELD>` as the codegen names them). It was checked bit for bit against the Java classes (`__tests__/moonlight-goldens.json`, synthetic images; the commands are in `__tests__/fixtures.ts`). `generateEcTexture` runs one recipe.
- **Not supported:** modules that draw extra assets in Java code (`addDynamicClientResources` overrides: `customClientResources`, reported as a warning), block-entity renderers (chests and similar), connected textures, the three special-wood post-processing overlays, tinting (`copyParentTint`), user configs, and modules other mods register through `EveryCompatAPI` from their own jars.
- **Per-release steps (Every Compat family):** update the four checkouts. If Moonlight's `Palette`, `Respriter` or colour classes changed, update `texture/` and its goldens. If the type registries or finders changed, update `block-types/`. If a builder method, transformer or `TextureGenHelper` changed, update `runtime.ts`, `assets.ts` and the generator. Then run `pnpm gen:everycomp`, check what it prints, and run `pnpm test`.
